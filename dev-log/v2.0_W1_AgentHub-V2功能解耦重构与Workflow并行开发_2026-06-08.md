## 架构决策记录（ADR）

### ADR-1: 模块命名规范
**决策**: `AgentHub-V2—功能模块名称`（em dash 连接）
**理由**: 用户明确要求；一眼可识别归属项目 + 功能域；避免了 npm scope 或 monorepo package 的工程复杂度

### ADR-2: 单 Vite 项目 vs Monorepo
**决策**: 单一 Vite 项目，模块通过 path alias + barrel export 解耦
**理由**: 避免 npm workspace 跨包依赖复杂度；模块间 import 零运行时开销（编译时 resolve 为相对路径）；vitest 可直接运行任意模块组合

### ADR-3: v1.1 资产复用
**决策**: AppShell/ClassicIMView 通过相对路径直接 import v1.1 组件和 store
**理由**: 不复制代码；v1.1 继续独立运行不受影响；切换到 Classic IM 零数据丢失

### ADR-4: BackendServices 补丁模式
**决策**: 输出纯函数补丁（patchSystemPrompt、parseAgentChunkForGenUI 等），不直接修改 server/
**理由**: 保持 v1.1 后端稳定；补丁函数可独立测试；应用时由开发者 review 差异后手动合并

### ADR-5: Workflow Phase 编排策略
**决策**: Phase 0（基础）→ Phase 1（3 并行）→ Phase 2（3 并行）→ Phase 3（集成验证）
**理由**: 依赖关系决定串行屏障点；无依赖模块最大并行化；每 Phase 末有独立验证 Agent

### ADR-6: Git 分支策略
**决策**: `AgentHub-V2` 作为孤儿分支，根目录即 V2 工程；master 保留完整 BD 项目含 `AgentHub-V2/` 子目录
**理由**: 方便独立 clone V2 项目（`git clone -b AgentHub-V2 --single-branch`）；master 保留开发上下文

## 经验总结

### 做得好的

1. **规范先行**: 8 份 spec markdown 在 Agent 启动前写完，每个 Agent 有精确的"施工图纸"，无需求歧义
2. **Phase 串并结合**: Phase 1/2 各 3 Agent 真正并行无冲突（操作不同目录），墙钟时间大幅压缩
3. **验证 Agent**: 每 Phase 末的 verify agent 做交叉检查，发现了 @xyflow/react v12 API 变更、stub 实现缺漏、类型不匹配等 10+ 问题
4. **v1.1 零侵入**: 47 个新文件全在 `AgentHub-V2/` 下，原有项目代码一行未改
5. **Git 分支干净**: 孤儿分支使得 `AgentHub-V2` 分支根目录即 V2 工程，可独立 clone 开发

### 教训

1. **Workflow 脚本不宜嵌入大段代码**: 首次尝试将完整代码嵌入 agent prompt 失败（模板字面量中的反引号导致 JS 解析错误）。改为写 spec markdown 文件 → agent 读取 spec → 实现，顺利解决
2. **第三方库版本差异需预判**: @xyflow/react v12 NodeProps 泛型约束与预期不同，需要 `NodeData & Record<string,unknown>` 交叉类型。下次应在 spec 中注明库的主版本号
3. **Stub 与 Test 同步问题**: Panels 模块最初创建了 stub 组件（空 props），测试期望完整实现，验证 Agent 补全。下次应要求 Agent 先读测试再实现
4. **孤儿分支操作风险**: 首次尝试在孤儿分支上 rm -rf 工作区文件时触发了安全拦截。改用"复制到临时目录 → 孤儿分支 → 搬回"的三段式安全方案
