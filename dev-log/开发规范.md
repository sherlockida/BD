# AgentHub 开发规范

> 提炼自《48小时Agent极限开发工程化规范》，结合 AgentHub v1.1 项目当前阶段（W2→W3）裁剪。与 RULES.md（Agent 行为约束）和 SPEC.md（平台规格）互补，本文件聚焦**开发过程纪律**。

---

## 一、核心约束（不可妥协）

### 1.1 MVP 保底
- 每个 Phase 结束时，必须有一个**可演示的版本**。
- 新功能不得破坏已有演示路径。任何 PR 合并前，在本地跑通完整的 P0 演示流程（新建群聊 → @PMO 发任务 → Plan Card → Agent 回复 → 产物卡片）。
- 如果一个功能在 2 小时内无法跑通，砍掉它，用 Mock 替代。

### 1.2 模块上限
- 单文件 ≤ **300 行**（React 组件）/ **500 行**（后端服务）。
- 超过上限必须先拆分再提交，拆分边界沿"采集 → 处理 → 存储 → 展示"四层。
- 当前已知超标风险点：`server/src/services/llmGateway.ts`（三厂商 SDK 混在一起，W3 考虑拆成 adapter 模式）。

### 1.3 回滚保障
- 每个 Phase 完成时打 Tag，格式：`v1.1-{phase}-{date}`，如 `v1.1-w2-20260604`。
- Tag 之前必须在本地验证：`npm run build` 通过 + P0 演示路径无报错。
- 当前缺失的 Tag：W0 (方案评审)、W1 (后端骨架)、W2 (LLM接入) — **立即补打**。

## 二、人机协作边界

### 2.1 分工铁律

| 维度 | 人（你） | AI（Claude Code） |
|------|---------|-------------------|
| 需求拆解 & 优先级 | **全权负责** | 只做方案解读和 trade-off 分析 |
| 架构设计 | **全权负责** | 只做多方案对比，不改架构决策 |
| Bug 根因分析 | **主导**（定位根因） | 辅助（搜索、日志分析） |
| 代码编写 | 核心业务逻辑手写 | 样板代码、Mock、测试、适配器 |
| 代码审查 & 合并 | **最终决策** | 只做静态检查和建议 |
| 文档撰写 | 审查修改 | 初稿生成 |

### 2.2 Prompt 编写规范
- **一次一个问题**：禁止在一个 Prompt 里塞多个不相关的需求。例如不要同时让 AI "加超时重试"和"改数据库 Schema"。
- **精确到函数签名**：给出函数名、参数类型、返回值格式、失败行为。例如：
  > 在 `llmGateway.ts` 中给 `chatWithAgent()` 添加 30s 超时：超时后抛出 `LLMTimeoutError`（继承自 Error），调用方在 `agents.ts` 路由中 catch 并返回 HTTP 504。
- **附上下文**：每次 Prompt 粘贴相关的接口定义和调用链路代码片段，不让 AI 猜。

### 2.3 代码接手标准
你必须能回答任何一个文件的这三个问题：
1. **调用链路**：谁调它，它调谁？（上游 ↓，下游 ↓）
2. **失败后果**：这个函数抛异常，用户看到什么？
3. **数据流向**：数据从哪里来，写到哪里去？

建议每完成一个模块，在 dev-log 里用 3 句话回答上述问题。

## 三、可靠性工程规范

### 3.1 外部调用必须三项齐全
所有外部 API（LLM、数据库、第三方服务）调用必须同时具备：
```
超时（timeout）  +  重试（retry）  +  兜底（fallback）
```

当前状态检查：

| 调用点 | 超时 | 重试 | 兜底 | 状态 |
|--------|------|------|------|------|
| `llmGateway.ts` → DeepSeek API | ❌ 缺失 | ❌ 缺失 | ✅ 降级到其他 provider | **W3 补充** |
| `llmGateway.ts` → Anthropic/OpenAI | ❌ 缺失 | ❌ 缺失 | ✅ 降级到 DeepSeek | **W3 补充** |
| `db/index.ts` → PostgreSQL | ✅ pg Pool 默认 | ❌ 缺失 | ❌ 缺失 | **加 health check 重试** |
| `wsServer.ts` → WebSocket | ❌ 缺失 | ✅ 前端自动重连 | ❌ 缺失 | **加心跳** |

**W3 行动项**：
- LLM Gateway 统一加 30s 超时 + 1 次重试（指数退避 1s→2s）
- PostgreSQL 连接失败时，健康检查端点返回降级状态（而非崩溃）
- WebSocket 加 30s 心跳 ping/pong

### 3.2 日志规范
- 所有外部调用入口/出口必须打日志：`[LLM] req: agent=codex, promptLen=234` / `[LLM] res: 234ms, tokens=567`
- 错误日志必须包含**足够排查问题的上下文**：`[LLM] err: DeepSeek timeout after 30s, agent=codex, retry=1/1, falling back to anthropic`
- 禁止：`console.log('error')` / `console.error(err)` 无上下文

### 3.3 Fallback 设计模式
```
主路径 (primary) → 降级路径 (fallback) → 优雅失败 (graceful)
     ↓                    ↓                      ↓
  正常响应           功能降级但可用          向用户明确报错
                                          + 提供手动操作入口
```

当前已实现：LLM provider 降级（deepseek ← anthropic/openai）。
W3 待实现：Planner LLM 路径失败 → 自动回退关键词 fast path；Agent 超时 → 系统消息"xxx 暂时不可用，请稍后重试"。

## 四、版本控制规范

### 4.1 Git 工作流
- **不在 master 直接推代码**（除文档/紧急 hotfix）。
- 使用 feature 分支：`feature/w3-artifact-parser`、`fix/llm-timeout`。
- 每个模块完成后提交独立 PR，commit message 格式：
  ```
  feat(server): LLM Gateway 添加 30s 超时和 1 次重试
  fix(frontend): WebSocket 断线重连后状态丢失
  ```

### 4.2 Tag 时间线（当前项目）
```
v1.1-w0-20260603  ← 方案评审 + 环境初始化（补打）
v1.1-w1-20260604  ← 后端骨架 + 数据库建表（补打）
v1.1-w2-20260604  ← LLM 真实接入 + 前后端联调（补打）
v1.1-w3-xxxxxx    ← 产物解析 + Planner 对接（即将）
v1.1-w4-xxxxxx    ← 部署 + 收尾
```

### 4.3 回滚判断标准
以下情况立即回滚到上一个 Tag：
- 演示路径出现不可快速修复的 Bug（>30 分钟）
- 新代码导致已有功能回归
- 外部依赖不可用且无 Fallback

## 五、会话管理规范

### 5.1 会话拆分
| 场景 | 独立会话 | 原因 |
|------|---------|------|
| 新功能开发 | ✅ 新会话 | 干净上下文，明确 Spec |
| Debug / 修 Bug | ✅ 新会话 | 专注问题域 |
| 部署 / 环境配置 | ✅ 新会话 | 减少干扰 |
| 代码审查 | ✅ 新会话 | 切换到审查视角 |

### 5.2 会话上限
- 单个 Session 对话不超过 **10 轮**。超过时开启新会话，并在第一条消息中附上：
  - 当前 Phase 目标
  - 最新 dev-log 路径
  - 关键决策记录
- **不依赖 AI 的记忆**：所有重要信息（架构决策、接口定义、Bug 根因）必须在会话结束前写入 dev-log 或 memory。

### 5.3 dev-log 写入时机
- 每个 Phase 完成时（必有）
- 每个关键决策做出时
- 每个 Bug 修复完成时（记录根因 + 修复方案）
- 格式沿用现有规范：`{版本号}_{第几阶段}_{修改内容简述}_{日期}.md`

## 七、技术选型红线

### 7.1 禁止引入
- ❌ LangChain / CrewAI / AutoGen 等重型 Agent 框架（已决策自研编排引擎，见 W0 决策 1）
- ❌ PostgreSQL 之外的新数据库（当前 pg 已够用，不要加 Redis 之外的存储）
- ❌ 未经验证的第三方 npm 包（npm 下载量 < 10k 或最后更新 > 1 年前，必须先人工审查）
- ❌ 新的部署平台（统一 Railway CLI，当前本地 Docker Compose 开发、Railway 生产）

### 7.2 推荐使用
- ✅ 现有技术栈内解决问题：Express + Drizzle ORM + WebSocket + React + Zustand
- ✅ 轻量工具库：只需验证功能单一、无依赖黑洞的小库
