## 1. 产品概述

### 1.1 产品定位

**AgentHub 是一个以 IM 群聊为核心交互范式的多 Agent 协作平台。** 它让 AI Agent 像人类同事一样"在群里上班"，用户通过飞书/微信式的对话体验，调度多个 AI Agent 完成从需求到交付的完整项目流程。

### 1.2 核心价值主张

| 痛点 | AgentHub 解法 |
|------|--------------|
| 单 Agent 能力有边界，复杂任务需要多 AI 协作 | PMO 智能编排器自动拆解任务、分派 Agent、聚合结果 |
| 主流 Agent 散落在浏览器/IDE/CLI，用户切换疲劳 | 统一 IM 界面，一个窗口管理所有 Agent |
| AI 产出物难以管理，缺少版本和迭代能力 | 产物内联预览 + append-only 版本历史 + Diff 视图 |
| AI 协作经验无法沉淀，每次对话从零开始 | Skills 一键沉淀 + RAG 召回，越用越聪明 |

### 1.3 产品一句话

> **"把多个 AI Agent 拉到一个飞书群里，让它们协作完成你的项目。"**

## 2. 市场背景与竞品分析

### 2.1 行业趋势

- **2024-2026 年 AI Agent 爆发**：Claude Code、Codex、OpenCode、Cursor、Devin 等工具百花齐放
- **从"单 Agent 对话"到"多 Agent 协作"**：CrewAI、AutoGen、LangGraph 等框架涌现
- **IM 范式被验证**：飞书/钉钉/Teams 已是企业协作事实标准

### 2.2 竞品对标

| 维度 | CrewAI | AutoGen | ChatGPT | Cursor | **AgentHub** |
|------|--------|---------|---------|--------|-------------|
| 交互范式 | CLI/Python | CLI/Python | 单聊 | IDE | **IM 群聊** |
| 多 Agent | ✅ 角色定义 | ✅ 对话流 | ❌ 单 Agent | ❌ 单 Agent | ✅ PMO 编排 |
| 产物管理 | ❌ 无 UI | ❌ 无 UI | ❌ 基础 | ✅ 代码 Diff | ✅ 多类型内联预览+版本历史 |
| 学习成本 | 高（需编程） | 高（需编程） | 低 | 中（IDE 习惯） | **极低（飞书习惯）** |
| AI 经验沉淀 | ❌ | ❌ | ❌ | ❌ | ✅ Skills 自沉淀 |
| GenUI 交互 | ❌ | ❌ | ❌ | ❌ | ✅ ChoiceCards 暂停/恢复 |

### 2.3 差异化定位

AgentHub 不做"又一个 Agent 框架"，而是做 **"Agent 协作的操作系统"** — 把"管理多个 AI"这件事变得像"管理一个飞书项目群"一样自然。

## 3. 用户画像与使用场景

### 3.1 核心用户

| 画像 | 特征 | 核心诉求 |
|------|------|---------|
| **独立开发者** | 1人团队，需要同时处理前后端/设计/文案 | 一句话需求 → 多 Agent 并行产出完整项目 |
| **产品经理** | 不会写代码，需要快速验证想法 | 自然语言描述需求 → 可视化预览 → 迭代修改 |
| **技术 Leader** | 管理多个项目，需要审计和治理 AI 产出 | 完整审计记录 + 版本历史 + Agent 行为约束 |
| **学生/学习者** | 学习 AI 协作开发范式 | 观摩 PMO 如何拆解任务、Agent 如何协作 |

### 3.2 典型使用场景

#### 场景一：独立开发者做落地页
```
用户: "做个茶饮品牌 H5 落地页，带表单收集留资"
→ PMO 拆解为 4 个子任务: 文案/HTML/CSS/表单验证
→ DocAgent + ClaudeCode + Codex + OpenCode 并行执行
→ 产物内联预览，用户圈选修改
→ 一键部署上线
```

#### 场景二：PM 验证产品 idea
```
用户: "我想做一个课程管理 SaaS，帮我出个原型"
→ PMO 拆解为: 页面结构/组件设计/数据模型/交互流程
→ Agent 产出交互式 HTML 原型
→ PM 在预览中体验 → 标注修改点 → Agent 迭代
```

#### 场景三：技术 Leader 代码审查
```
用户: "审查这个项目的安全性"
→ PMO 分派给多个 Agent 从不同维度审查
→ 每个 Agent 产出审查报告
→ PMO 聚合为综合审查报告
```

## 4. 核心功能设计

### 4.1 IM 聊天式交互（核心体验）

**设计原则**：零学习成本，复用用户对飞书/微信的肌肉记忆。

```
┌──────────┬───────────────────────┬──────────┐
│ 对话列表  │     聊天窗口           │ 产物面板  │
│ (左栏)   │     (中栏)            │ (右栏)   │
├──────────┼───────────────────────┼──────────┤
│ 🔍搜索   │ ┌─────────────────┐  │ 预览|代码 │
│ [+]新建  │ │ PMO Plan Card   │  │ Diff|历史│
│ ──────── │ │ ┌──┬──┬──┬──┐  │  │          │
│ 📌项目A  │ │ │子│子│子│子│  │  │ ████████ │
│ 🤖Claude │ │ │任│任│任│任│  │  │ ████████ │
│ 🤖Codex  │ │ └──┴──┴──┴──┘  │  │ ████████ │
│ 📦归档   │ │                 │  │          │
│          │ │ 🤖Claude Code   │  │          │
│          │ │ 这是 index.html │  │          │
│          │ │ ┌───────────┐  │  │          │
│          │ │ │ 预览卡片   │  │  │          │
│          │ │ └───────────┘  │  │          │
│          │ │                 │  │          │
│          │ ├─────────────────┤  │          │
│          │ │ 输入框  [发送]  │  │          │
│          │ └─────────────────┘  │          │
└──────────┴───────────────────────┴──────────┘
```

**功能矩阵**：

| 功能 | 说明 | 状态 |
|------|------|------|
| 对话列表 | 新建/置顶/归档/搜索/重命名/删除，按 pinned+活跃排序 | ✅ |
| 单聊模式 | 1v1 与单个 Agent 对话 | ✅ |
| 群聊模式 | @ 多个 Agent，PMO 自动编排 | ✅ |
| 消息类型 | 文本/代码块/Plan Card/产物卡片/Deploy Card/系统通知 | ✅ |
| 消息操作 | Pin/引用/重新生成/复制代码/一键应用 Diff | ✅ |
| 流式渲染 | typing indicator + cursor 动画，边收边渲染 | ✅ |
| 上下文管理 | 完整聊天历史 + Pin 消息优先注入 | ✅ |

### 4.2 PMO 智能编排器（Orchestrator 2.1）

**设计理念**：PMO（Project Management Officer）是"AI 项目经理"，模拟人类 PM 的完整工作流。

```
用户意图 → Classifier(意图分类) → AgentSelector(智能选人)
                                        ↓
                                  Planner(任务拆解→DAG)
                                        ↓
                               Supervisor(并行调度+监控)
                                        ↓
                              Blackboard(上下文黑板共享)
                                        ↓
                              Critic(质量审查+打回)
                                        ↓
                              Synthesizer(聚合→PMO周报)
```

**编排能力**：

| 能力 | 说明 |
|------|------|
| 意图分类 | 自动区分"需要编排的复杂任务"vs"直接对话的简单问题" |
| 智能选人 | 根据 Agent capability tag 匹配最合适的执行者 |
| DAG 拆解 | LLM 驱动，输出有依赖关系的子任务图 |
| 并行调度 | 无依赖任务并行，有依赖的拓扑排序等待 |
| 容错降级 | 上游失败不阻塞下游，失败 Agent 自动 fallback 切换 |
| 黑板共享 | 子 Agent 可通过 Blackboard 读取前置任务的产物上下文 |
| GenUI 暂停 | Agent 输出 ChoiceCards 等交互组件时暂停等待用户输入 |
| Saga 补偿 | 30 分钟无响应自动降级，保证流程不永久阻塞 |
| Trace 追踪 | 全链路执行追踪，每个任务有明确的 started/completed/failed 状态 |

### 4.3 多 Agent 接入

**统一适配器层**：

```
IAgent (接口契约)
  ├── ClaudeCodeAgent → Anthropic API
  ├── CodexAgent      → OpenAI API
  ├── OpenCodeAgent   → 自托管/开源 LLM
  └── CustomAgent     → 用户自建（System Prompt + 工具集）
```

**Agent 市场**：
- 浏览所有可用 Agent（头像/名称/能力标签/状态）
- 一键自建 Agent（对话式：描述 → 生成 System Prompt → 注册入库）
- Agent 健康检查 + 状态展示

### 4.4 产物预览与编辑

**支持的产物类型**：

| 类型 | 预览方式 | 编辑能力 |
|------|---------|---------|
| Webpage | iframe 沙箱渲染（三层安全：CSP + 运行时注入 + sandbox） | Monaco Editor + 圈选修改 |
| Code | 语法高亮 + Monaco 全功能编辑器 | Diff 视图 + 版本回滚 |
| Document | Markdown 渲染 | 源码编辑 |

**产物管理**：
- Append-only 版本时间线（v1 → v2 → v3...）
- 行级 Diff 视图（+/- 双列对比）
- 一键回滚到任意历史版本
- 同轮去重：同一编排轮次内同名产物自动加 Agent 后缀

### 4.5 Skills 知识沉淀

**设计理念**：每次协作都是学习机会，让平台越用越聪明。

```
协作完成 → PMO 提议沉淀 → 用户确认 → 生成 Skill.md
                                              ↓
                                   下次类似对话自动 RAG 召回
```

- 5 条内置 Skill：Agent 适配器模式、编排器任务规划、IM 流式消息、产物版本控制、人机协作协议
- 用户手动触发：hover Agent 消息 → ✨ 一键沉淀
- 召回机制：按 trigger 关键词在新对话中自动匹配

## 5. 交互设计

### 5.1 设计语言

基于飞书设计语言裁剪：

- **配色**：飞书蓝 (#3370FF) 为主色调，中性灰背景
- **圆角**：8px（卡片）/ 12px（气泡）
- **阴影**：轻量投影，层次分明
- **动效**：消息滑入 (slide-up) + typing 三点跳动 + cursor 闪烁

### 5.2 布局

三栏布局（桌面端主力形态）：
- **左栏** (280px)：对话列表 + 底部工具栏
- **中栏** (flex-1)：聊天窗口 + 输入框
- **右栏** (可折叠)：产物面板（预览/代码/Diff/历史）

### 5.3 关键交互流

**群聊协作流**：
```
[新建群聊] → [选择Agent/输入需求] → [PMO Plan Card弹出]
→ [子任务逐个执行(流式)] → [产物卡片内联]
→ [点击展开预览] → [圈选代码→@Agent修改] → [迭代完成]
→ [/deploy部署] → [PMO周报+Skill沉淀建议]
```

**乐观更新 + 失败回滚**：
```
用户操作 → Zustand即时更新 → API请求
    ↓                            ↓
  UI已响应                  成功→无事发生
                            失败→回滚状态+系统消息通知
```

## 6. 技术产品化设计

### 6.1 技术选型的产品考量

| 技术决策 | 产品理由 |
|---------|---------|
| 自研编排器（非 CrewAI/LangGraph） | IM 群聊范式需要定制调度，框架绑定会限制交互自由度 |
| Drizzle ORM（非 Prisma） | 更轻量，SQL-like API，适合快速迭代 |
| SSE + WebSocket 双通道 | SSE 用于流式聊天（单向），WS 用于实时事件（双向广播） |
| 前端 Mock First | 先验证交互范式，真实 API 接入只需替换 Adapter 层 |
| 乐观更新模式 | 聊天应用对延迟敏感，不能等 API 返回才显示消息 |

### 6.2 可靠性设计

- **LLM Gateway**：超时 30s + 指数退避重试 + provider 降级（deepseek ↔ anthropic ↔ openai）
- **DAG 容错**：上游失败 → 下游带警告继续，不阻塞整个编排
- **数据库**：每条连接 SET client_encoding = 'UTF8'，解决中文乱码
- **WebSocket**：30s 心跳 ping/pong 保活
- **Hydration 自愈**：DB 为空时自动持久化本地 demo 数据

## 7. 创新亮点

### 7.1 "Agent 在群里上班" 范式

**创新点**：把"人管理 AI"的模式从"命令行/API"升级为"群聊协作"。

飞书/微信有 10 亿用户，所有人都会用群聊。AgentHub 让 AI Agent 成为群里的"数字同事"，这是最低学习成本的多 Agent 交互范式。

### 7.2 PMO 拟人化编排

**创新点**：不是冷冰冰的任务队列，而是有"项目管理思维"的 AI 经理。

PMO 输出 Plan Card（可视化任务图）→ 并行调度 → 失败时主动汇报 → 全部完成后写"PMO 周报" → 主动建议沉淀 Skill。整套流程模拟人类 PM 的行为模式。

### 7.3 Generative UI 暂停/恢复

**创新点**：Agent 不是一次性跑到底，可以在需要用户决策时"停下来问"。

Agent 输出 ChoiceCards → 任务进入 paused 状态 → 用户选择 → 任务恢复执行。这解决了"全自动 vs 全手动"的二元对立，实现了真正的人机协作。

### 7.4 Skills 自沉淀机制

**创新点**：不只是"这次做完了"，而是"下次更聪明"。

每次协作结束，PMO 会分析本次对话中可复用的经验，主动提议沉淀为 Skill。Skill 在新对话中按 trigger 自动召回 — 这是 AI 协作的"组织学习"。

### 7.5 Canvas 车间隐喻（v2.0 设计提案）

**创新点**：把传统的"聊天窗口"升级为"数字车间"。

Agent 不是"在聊天框里回答问题"，而是"在画布上操作实体"。用户可以看到 Agent 的"手"在拖拽组件、修改代码、调整布局 — 从"对话式"升级为"可视化协作"。这是从 ChatGPT 到 Figma 的范式跨越。

## 9. 设计决策记录

### 决策 1：为什么是 IM 范式而不是 IDE 范式？

- IDE（如 Cursor）适合"写代码"场景，但多 Agent 协作本质是"沟通+协调"
- IM 范式天然支持多角色对话、消息流、引用回复、上下文连续
- 零学习成本：用户不需要学新工具，飞书怎么用 AgentHub 就怎么用

### 决策 2：为什么自研编排器而不是用 CrewAI/LangGraph？

- 这些框架设计目标是"Python 脚本中的多 Agent 流程"，不是"IM 聊天中的实时协作"
- 我们的核心交互（Plan Card 可视化、GenUI 暂停/恢复、用户中途干预）无法用现有框架表达
- 自研编排器 = 完全的交互自由度

### 决策 3：为什么乐观更新？

- 聊天场景对延迟极度敏感（>200ms 用户就能感知）
- 先更新 Zustand 获得即时响应 → API 静默同步 → 失败时回滚
- 这是 WhatsApp/飞书的通用做法

### 决策 4：为什么 append-only 产物版本？

- 审计可追溯（谁在什么时候产出了什么）
- 回滚安全（不是删除，而是新增 revert 版本）
- 符合 Git 心智模型
